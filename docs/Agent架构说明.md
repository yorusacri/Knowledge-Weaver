# Agent 架构说明

## 1 架构总览

本系统采用**单 Agent 主控 + 多模块协作**的架构，而非复杂的多 Agent 协作网络。

```
┌──────────────────────────────────────────────────────────────────┐
│                       用户交互层（Web SPA）                        │
└────────────────────────────┬───────────────────────────────────┘
                             │ HTTP
┌────────────────────────────▼───────────────────────────────────┐
│                    Agent 主控（LLM 调度器）                       │
│  • 理解用户意图（上传/图谱/整合/RAG/对话）                         │
│  • 路由到对应功能模块                                              │
│  • 管理对话历史上下文                                              │
└──────┬──────────┬──────────┬──────────┬─────────────────────────┘
       │          │          │          │
┌──────▼──┐ ┌─────▼───┐ ┌───▼────┐ ┌───▼────────┐
│解析模块 │ │图谱模块 │ │整合模块│ │RAG模块     │
│(Parser)│ │(Graph)  │ │(Integr)│ │(RAG Engine)│
│        │ │         │ │        │ │            │
│ PDF    │ │节点提取 │ │语义对齐│ │分块        │
│ MD     │ │关系识别 │ │合并决策│ │嵌入       │
│ TXT    │ │频次统计 │ │去重提纯│ │检索       │
│ DOCX   │ │可视化  │ │压缩比  │ │生成+引用  │
└────────┘ └─────────┘ └────────┘ └────────────┘
```

**核心 Agent 以 LLM 为核心决策单元**，通过以下方式与各功能模块协作：
- 知识点提取（调用 LLM 逐章节提取节点和边）
- 跨教材语义对齐（Embedding + LLM 仲裁）
- RAG 生成（检索 + LLM 生成带引用的回答）
- 对话式整合决策调整（用户反馈 → Agent 决策调整 → 图谱更新）

## 2 为什么选择单 Agent 主控架构

### 2.1 替代方案分析

| 方案 | 优点 | 缺点 |
|------|------|------|
| 多 Agent 协作（Parser Agent + Graph Agent + RAG Agent）| 职责清晰，可并行 | Agent 间通信复杂，上下文传递成本高 |
| **单 Agent 主控** | **架构简单，决策集中，上下文共享** | **需要精心设计 prompt避免角色混乱** |
| 无 Agent（纯规则系统） | 可预测，无幻觉 | 无法处理歧义，扩展性差 |

### 2.2 设计决策

**选择单 Agent 主控的理由：**

1. **上下文自然共享**：知识图谱构建的中间结果（节点列表）可直接用于 RAG 检索，无需跨 Agent 传输序列化数据

2. **对话式交互的自然优势**：多轮对话场景中，用户可能交替询问图谱问题、RAG 问题、整合问题——单 Agent 天然能追踪上下文，而多 Agent 需要额外的协调层

3. **黑客松时间约束**：5 小时内，多 Agent 的通信协议设计、状态同步会消耗大量时间，单 Agent 只需设计好 prompt 和路由逻辑

4. **API 调用成本**：多 Agent 之间每步传递都需要 LLM 调用，成本叠加；单 Agent 通过共享上下文减少重复调用

### 2.3 如何管理 Prompt 复杂度

**采用分层 prompt 设计：**

```
System Prompt（全局约束）
  └── "你是学科知识整合智能体..."
  └── 输出格式约束（JSON Schema）
  └── 引用约束（必须附带 [教材, 章节, 页码]）

Module-level Prompt（按功能模块）
  └── 知识提取 Prompt
  └── 语义对齐 Prompt
  └── RAG 生成 Prompt

In-context Examples（few-shot）
  └── 每个 Module Prompt 附带 2-3 个示例
```

**按调用阶段注入上下文，而非全量加载：**
- 知识提取：只注入当前章节的内容
- 语义对齐：只注入待对齐的节点对
- RAG 生成：只注入 top-5 相关 chunks

## 3 各模块设计

### 3.1 解析模块（Parser Agent）

**职责：**将 PDF/MD/TXT/DOCX 解析为统一的 `ParsedTextbook` 结构

**设计决策：**
- PDF 解析使用 **PyMuPDF 逐页处理**，而非一次性加载整书 → 避免内存溢出
- 章节识别采用 **规则为主 + LLM 为辅** 的策略：
  - 规则：正则匹配"第X章" + 字体大小 + TOC 提取
  - LLM fallback：若规则识别 < 2 章，调用 LLM 识别章节边界
- 支持格式：PDF（必须）、Markdown（必须）、TXT（必须）、DOCX（建议）

**输入：**文件路径
**输出：**`ParsedTextbook` JSON

### 3.2 图谱模块（Graph Agent）

**职责：**从章节内容中提取知识点，构建知识图谱

**设计决策：**
- **逐章节调用 LLM**，每次只处理一个章节的内容 → 避免上下文过长
- 节点关系类型：至少 3 种（prerequisite, parallel, contains, applies_to）
- **embedding 频次统计**：同名称节点在不同教材中出现 → 跨教材时节点频率 > 1，用于图谱可视化的大小/颜色映射

**输入：**章节内容
**输出：**`{nodes: [], edges: []}`

### 3.3 整合模块（Integration Agent）

**职责：**跨教材去重提纯，执行整合决策

**设计决策：**
- **双重对齐机制**：
  1. Embedding 相似度初筛（阈值 > 0.85 → 自动合并）
  2. 阈值 0.70~0.85 → LLM 仲裁判断是否等价
  3. 阈值 < 0.70 → 保留为不同知识点
- **决策类型**：`merge`（合并重复）、`keep`（保留唯一）、`remove`（删除冗余）
- **压缩比控制**：实时统计整合后字数，确保 ≤ 30%

**输入：**多本教材图谱
**输出：**整合决策列表 + 更新后的图谱

### 3.4 RAG 模块（RAG Agent）

**职责：**基于向量检索的精准问答

**设计决策：**
- **分块策略**：500-800 字/块，50-100 字滑动窗口重叠
- **embedding 模型**：BGE-small-zh（支持中文，本地运行）
- **向量存储**：FAISS（CPU 友好，亿级向量高速检索）
- **生成约束**：Prompt 要求 LLM 只基于检索到的上下文回答，且必须附带 `[教材, 章节, 页码]` 引用

**输入：**用户问题
**输出：**`{answer, citations[], source_chunks[]}`

### 3.5 对话模块（Dialogue Agent）

**职责：**支持教师通过自然语言修改整合决策

**设计决策：**
- 对话历史在内存中持久化（会话级）
- 用户反馈（如"保留XX"）→ Agent 解析意图 → 调用 `/api/integration/decisions/{id}` 修改决策 → 更新图谱
- 每项整合决策附带 `reason` 字段，便于 Agent 解释决策依据

**输入：**用户消息
**输出：**Agent 回复

## 4 数据流与调用链路

### 4.1 完整流程：上传教材 → 构建图谱 → 整合 → 问答

```
用户上传教材
    │
    ▼
POST /api/textbooks/upload
    │ 文件存入 data/uploads/
    │ 后台进程开始解析
    ▼
Parse → ParsedTextbook JSON
    │
    ▼
POST /api/graph/{id}/build
    │ 逐章节调用 LLM
    ▼
Graph JSON（节点+边）
    │
    ▼
加载多本教材图谱后：
POST /api/integration/run
    │ Embedding 相似度初筛
    │ LLM 仲裁
    ▼
整合决策列表 + 压缩比
    │
    ▼
POST /api/rag/index
    │ 分块 + embedding + FAISS
    ▼
向量索引就绪
    │
    ▼
用户提问：
POST /api/rag/query
    │ 检索 top-5 chunks → LLM 生成
    ▼
带引用的回答
```

### 4.2 关键接口输入输出

| 接口 | 输入 | 输出关键字段 |
|------|------|-------------|
| `/api/textbooks/upload` | multipart file | `textbook_id`, `status` |
| `/api/graph/{id}/build` | `textbook_id` | `status: building` |
| `/api/integration/run` | 无 | `decisions[]`, `compression_ratio` |
| `/api/rag/query` | `{question}` | `answer`, `citations[]` |
| `/api/dialogue/message` | `{content}` | `{role, content, timestamp}` |

## 5 RAG Pipeline 设计

### 5.1 分块策略

```
分块粒度：500-800 字符/块
滑动窗口：50-100 字符重叠
元数据保留：textbook_id, chapter, page
```

**为什么选择这个粒度：**
- 500-800 字约等于 250-400 tokens，在 LLM 上下文窗口中占比适中（<10%）
- 医学核心概念（定义+描述）通常在这个长度范围内
- 超出范围会稀释语义焦点，低于此范围则上下文碎片化

### 5.2 Embedding 与检索

```
Embedding 模型：sentence-transformers / BGE-small-zh
向量数据库：FAISS (IndexFlatIP, L2 距离)
检索方式：top-5 向量检索
```

**Top-5 选择理由：**
- 太少（<3）可能遗漏相关信息
- 太多（>10）会引入过多噪声，稀释 LLM 的回答质量
- 5 是平衡精确率和召回率的合理选择

### 5.3 生成 Prompt 约束

```
1. 只基于提供的上下文回答，不使用模型自身知识
2. 每个回答必须附带来源引用：[教材名称, 第X章, 第X页]
3. 如果上下文中找不到答案，回复"当前知识库中未找到相关信息"
4. 优先使用最相关的引用（relevance_score 最高的）
```

## 6 取舍与权衡

### 6.1 放弃的方案

| 放弃的方案 | 原因 |
|-----------|------|
| 多 Agent 协作架构 | 5 小时时间约束不允许设计 Agent 间通信协议 |
| ChromaDB（向量存储） | FAISS 更轻量，CPU 部署更简单 |
| 混合检索（向量+BM25） | 实现复杂度高，黑客松时间内难以保证质量 |
| 多视图切换（力导向图/树状图等） | 图谱交互是 P0 要求，多视图是 P1 加分项，先保证核心功能 |

### 6.2 已知局限

1. **跨语言知识点对齐**：当前 embedding 模型对中英混合文本的语义理解有限，"leukocyte"和"白细胞"的相似度可能不高
2. **实时图谱更新**：整合决策修改后，图谱数据需要重新计算，当前是全量重建而非增量更新
3. **并发解析限制**：最多 2 个并行解析进程，防止内存溢出，但会拖慢大文件解析

### 6.3 未来改进方向

1. **多 Agent 扩展**：将 RAG 检索和生成分离为独立 Agent，可并行执行，提升响应速度
2. **混合检索 Rerank**：引入 BGE-reranker 或 CrossEncoder 进行二次排序，提升检索精确率
3. **教学路径推荐**：基于知识图谱的 prerequisite 关系链，自动推荐学习路径
4. **持久化向量索引**：当前重启服务后需要重新构建索引，可接入 ChromaDB 等支持持久化的向量库
